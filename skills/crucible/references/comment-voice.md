# PR Comment Voice (Default)

Used by Crucible whenever drafting or posting GitHub PR comments—top-level comments, inline review comments, replies to bots or reviewers, and explanations—unless overridden by `hooks.commentVoiceSkill`.

PR descriptions, commit messages, and verbatim user-supplied text keep their own format.

## 1. Pin who is speaking and to whom

Before drafting, confirm the role (`gh pr view <url> --json author` when unsure):

- **Author answering feedback:** State what changed and which commit SHA fixed it, or explain concretely why a finding does not hold.
- **Reviewer:** Lead with the verdict on the PR, address the author directly, and do not thank anyone for a review you are writing. When endorsing points raised by another reviewer, state it once instead of replying as if their review were directed at you.
- **Replying in a thread:** Answer the specific comment while keeping the author/reviewer role above.

## 2. Disclosure box for substantive comments and reviews

When posting a review or substantive analysis/rebuttal comment generated by an agent, start with an accurate notice box in the comment's language. **Never claim manual review when the comment is posted autonomously.**

- **Autonomous run (not manually reviewed by the user):**

```markdown
> [!NOTE]
> Generated autonomously by <model> on behalf of @<username>.
```

- **Human-reviewed standalone comment/review:**

```markdown
> [!NOTE]
> Reviewed manually by @<username>, augmented with analysis and comment generated by <model>.
```

Use the actual GitHub login and model name—never leave placeholders. Keep the notice box for reviews and substantial analyses/rebuttals; a short `"Fixed in <sha> — ..."` reply does not need it.

## 3. Tone & structure

Write in a direct, warm, evidence-first voice. Do not open with canned thanks or a recap of the other person's points—warmth comes from respectful phrasing, not preamble.

- **Lead with the conclusion.**
- **Cite the code:** name exact files, lines, behaviors, tests, or reproduction steps.
- **Keep every sentence purposeful:** a finding, a reason, or a concrete question.
- **Distinguish verified facts from judgment.**
- **Assume good intent:** frame suggestions constructively, and when something is genuinely well done, say so in one plain sentence.

## 4. Safety checks before posting

1. Check the entire comment (including quoted code and attachments) for secrets, tokens, or private internal details.
2. Verify Markdown formatting (quotes, code fences, blank lines) before posting.
3. Outside an autonomous signed Crucible run, if the user only asked to draft/prepare a comment, show the finished Markdown and wait for approval before posting.
4. After posting, verify GitHub returned the comment or review URL. Only resolve a review thread (when authorized) after the reply has posted successfully.
